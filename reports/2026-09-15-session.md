## 4. Reconcile job fix

Make the launchd reconcile agent actually run every 15 minutes.

### Verification

No verification table was requested for this run. The output it produced:

**The plist was never misconfigured**

```
run interval = 900 seconds   runs = 379   last exit code = 0   state = not running
```

Against an expected 96 runs/day it managed 1–21, and none at all on 10–12 Sep.

**Cause 1 — runs outlasting their own interval (fixed)**

```
RUN 1 (cold ledger)   31 OK, 0 failed, 0 already confirmed, 31 newly confirmed    22.8s
RUN 2 (warm ledger)    0 OK, 0 failed, 31 already confirmed                        1.4s
```

Steady-state runs went from 22.8 s to **1.4 s with zero HTTP requests**, so a
run can no longer swallow the next interval. Log showed prior runs of 10, 21, 23
and **61 minutes**.

Two safety tests on the new ledger:

| Test | Result |
|---|---|
| Remove one entry from the ledger | exactly that one message re-posted: `1 OK, 0 failed, 30 already confirmed, 1 newly confirmed` |
| Corrupt the ledger | degrades to a full re-confirm: `31 OK, 0 failed, 0 already confirmed, 31 newly confirmed` |

**Cause 2 — the Mac sleeps after 1 minute (not fixed in code)**

```
Battery Power:  sleep 1
AC Power:       sleep 1
```

`StartInterval` does not wake a sleeping Mac; launchd coalesces every missed
slot into one run on wake, which is the pattern in the log. No plist change can
fix it. `sudo pmset -c sleep 0` was recommended.

### Files changed

- `scripts/reconcile_messages.py`

### Skipped or partial

**Cause 2 was not fixed.** It needs a `sudo pmset` change on the operator's
machine, which this session could not make and did not confirm was applied.

### Flagged as uncertain at the time

The new ledger records a message only when the app answers `duplicate:true`
**and** names the transaction — a bare 200 is not enough, because on some paths
the insert happens after the response and a few message shapes never produce a
transaction at all. Flagged as the design choice that keeps the ledger from
becoming a way to lose a message.

**IST / UTC offset**

`internalDate` is a UTC millisecond epoch.

```
internalDate  1789469352000  →  2026-09-15T10:49:12.000Z  →  IST 15/09/2026 16:19:12
body          "Sep 15, 2026 at 04:19:02"
offset        UTC+5:30, plus 10 s of ICICI send delay
```

**Did the format change over 24 months?**

The credit-card alert template did **not** change — the 09/03/2025 body and the
15/09/2026 body are the same template; only the sender domain moved. Everything
else did differ:

- Four time formats across alert types. Card alerts are 12-hour with **no
  meridiem** (`04:19:02` = 16:19 IST). NEFT/IMPS are 12-hour **with** `p.m.`
  iMobile transfers are **24-hour** (`at 14:40 hours`). ATM and interest alerts
  carry a date with no time.
- NEFT and IMPS subject lines do not exist before 2026. The old-domain
  equivalent was `Transaction alert for your ICICI Bank Mobile Banking`
  (iMobile Fund Transfer).
- Almost every body is **HTML-only**; of those fetched, only the ATM alert had
  a `text/plain` part.
